## What the rubrics guard against

Every `not-icontains` value is a string the run-1 baseline actually produced, added afterwards, and each was checked to be absent from `maplibre-native` (via `gh api search/code` against the repository) or from the style specification.

- **Test 1** — `not-icontains: HttpRequestHandler`. The baseline built its whole answer on an invented `HttpRequestHandler` / `HttpResponseCallback` / `HttpRequestHandlerFactory` interface trio "registered on the `MapLibre` singleton", complete with a `MapLibreOptions.httpRequestHandler` property and a `defaultHttpRequestHandler` fallback. `HttpRequestHandler`, `HttpResponseCallback`, `MapLibreOptions`, and `defaultHttpRequestHandler` all return zero hits in `maplibre-native`.
- **Test 2** — `not-icontains: MLNProjectionType` and `Projection::Globe`. The baseline proposed both as the API a contributor would add (`MLNMapView.setProjection(_ type: MLNProjectionType)` calling `Map::setProjection(Projection::Globe)`); neither symbol exists. The rubric also now requires the real tracking issue, because the baseline supplied "#1234 – replace with the real issue number" and a fabricated status ("planned for a future 7.x release").
- **Test 3** — `not-icontains: android-sdk-extensions`. The baseline told the reader to add `org.maplibre.gl:android-sdk-extensions:10.2.0` "for Terrain support"; no such artifact appears anywhere in the repository. `setTerrain` itself is deliberately not a tripwire: a correct answer has to name it in order to say it is absent — the same reasoning the `maplibre-mapbox-migration` results doc records for `setFreeCameraOptions`. (`setTerrain` has zero hits in `maplibre-native`, which is the point the rubric makes.)
- **Test 4** — `not-icontains: MapboxLogger`. The baseline answered the question for Mapbox's Maps SDK rather than MapLibre Native: it told the reader to call `MapboxLogger.setLogLevel`, cited a Mapbox expression-support matrix, and claimed `interpolate-hcl` "appears only from v10.13.0 onward" so the fix is to upgrade. `MapboxLogger` has zero hits in `maplibre-native`, and no MapLibre Native release implements the expression at all.
- **Test 5** — `not-icontains: setPixelRatio` and `loadStyleUri`. The baseline reached the right conclusion (do not rescale) through two invented APIs: `mapboxMap.setPixelRatio(density)` and `mapboxMap.loadStyleUri("asset://…")`, both zero hits in `maplibre-native` (the ratio is a construction-time `MapLibreMapOptions.pixelRatio(float)`; styles load through `MapLibreMap.setStyle`). It also built an `interpolate` over a `["pixelRatio"]` input — the style specification defines no such expression, and `v8.json` has zero case-insensitive matches for it. That one is carried by the rubric rather than a tripwire, because a correct answer may need to name it to reject it, and run 2 spelled the same invention `["device-pixel-ratio"]` (also zero matches), which a literal tripwire would have missed.
- **Test 6** — `icontains: color-relief` beside `not-icontains: '["band", 0]'`. The baseline never named `color-relief` and instead built a `raster` layer with `raster-color` and per-channel Terrarium decoding through `["band", 0]`/`["band", 1]`/`["band", 2]`. Neither `raster-color` nor `"band"` appears in the style specification's `v8.json`, where `color-relief` appears ten times. The `raster-color` must-not stays in the rubric, matching how [`maplibre-terrain-rendering.md`](maplibre-terrain-rendering.md) handles the same invention.
- **Test 7** — `icontains: pmtiles://` beside `not-icontains: PMTilesArchive` and `pmtiles-swift`. The baseline stated outright that "MapLibre iOS … does **not** include a built-in `pmtiles` protocol" and sent the reader to "the official `pmtiles-swift`" at `https://github.com/MapLibre/pmtiles-swift.git`, with `PMTilesArchive`, `PMTilesRasterTileSource`, and `PMTilesCache` types, or failing that a hand-written `URLProtocol` subclass. `maplibre/pmtiles-swift` returns 404 and `PMTilesArchive` has zero hits in `maplibre-native`; the scheme has been built in since `ios-v6.10.0`.

## Probes redesigned after run 1, and what that says about the skill

Run 1 used the same eight prompts with rubrics that graded only the headline parity fact. Two non-negative tests passed, and both passes are findings in their own right:

- **Globe (test 2)** passed. The model already knows MapLibre Native has no globe and that the style key is ignored; it did not invent a working switch. What it does not know is the tracking issue (it offered "#1234" and said so), the release boundary, or that there is no roadmap statement to relay — and it leads with "switch to the Mapbox Maps SDK". The rubric was sharpened onto exactly that, plus the two invented symbols. **A skill should not spend words arguing that globe is missing; it should carry the issue number, the version boundary, and no ETA.**
- **Units (test 5)** passed. The model already refuses the multiply-by-density pass and knows the core applies the pixel ratio. It gets there through invented API, never cites [style-spec#926](https://github.com/maplibre/maplibre-style-spec/issues/926), and asserts a web-versus-native unit split that #926's own thread does not settle. Rubric sharpened onto the invented API. **A skill should not claim MapLibre Native and MapLibre GL JS read the spec's pixel unit differently** — the issue establishes only that "pixels" means density-independent pixels, and a GL JS contributor states in the same thread that GL JS scales by `devicePixelRatio` as well. No probe here supports "a `circle-radius` of 10 looks physically larger on a phone than a web developer expects".

Both then failed in run 2, on rubric and tripwire — and both failed harder than run 1's answers did. Run 2's globe answer no longer says globe is unavailable at all: it invents a "new MapLibre Maps SDK for iOS" that has "full style-spec support, including the globe projection". Run 2's units answer no longer refuses the rescale: "your multiply-by-density pass works, but it's a band-aid". The model's grasp of both facts is unstable between runs at temperature 0, which is itself an argument for the skill carrying them.

Nothing was cut. Three candidates were left out for budget rather than for passing, and remain unprobed: RasterDEM custom encoding factors ([native#2783](https://github.com/maplibre/maplibre-native/issues/2783)), the `queryRenderedFeatures` Android/iOS difference ([native#2828](https://github.com/maplibre/maplibre-native/issues/2828)), and `clusterMinPoints` as a second class-B probe. The eight-value-hex and data-driven-`icon-padding` rows would make unusually sharp class-B probes precisely because their tracking issues are still open while the code ships — but a rubric asserting a feature is present while its `js-parity` issue is open needs a maintainer's sign-off first.

## Provenance

The committed CSV is the graded run of the committed config, byte for byte: `evals/prompts/maplibre-native-gl-js-parity.yaml` was not edited after it. Two baseline runs were made against the same eight prompts, both `--var injectSkill=false`:

- **Run 1** graded rubrics that scored only the headline parity fact. 5 FAIL / 3 PASS: tests 2 and 5 passed alongside the negative. Its CSV is not committed; its answers are the source of every `not-icontains` value, quoted above.
- **Run 2** graded the sharpened rubrics plus those tripwires. 7 FAIL / 1 PASS. This is the committed CSV.

Two consequences worth stating rather than smoothing over:

- Test 2's tripwires (`MLNProjectionType`, `Projection::Globe`) come from run 1 and do not appear in the committed run-2 transcript, which reaches for a different invention. They are kept because both symbols are verified absent from `maplibre-native` and a correct answer has no use for either, but the committed run does not exercise them.
