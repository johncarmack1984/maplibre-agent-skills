## What the guide already covers

The [Leaflet migration guide](https://maplibre.org/maplibre-gl-js/docs/guides/leaflet-migration-guide/) is eight short sections, each a Leaflet snippet beside its MapLibre equivalent: install (`npm install maplibre-gl`); map construction (`new Map({container, style, center, zoom})`); markers (`new maplibregl.Marker().setLngLat().addTo(map)`); a GeoJSON layer (`map.on('load', ...)` wrapping `addSource({type: 'geojson'})` plus `addLayer({type: 'fill'})`); click events (`event.latlng` → `event.lngLat`, given its own section with both sides); popups (`new maplibregl.Popup().setLngLat().setHTML().addTo(map)`); a custom raster tile layer (`tiles: [...]`, `tileSize: 256`); and a polygon (a geojson source with an inline Feature, coordinates flipped to `[lng, lat]`).

That means three of the five failure areas suggested in the [#76 review comment](https://github.com/maplibre/maplibre-agent-skills/issues/76#issuecomment-5475270202) — source/layer separation, the `map.on('load')` requirement, and `e.latlng` vs `e.lngLat` — are in the guide as working code, and a skill restating them would duplicate it. What the guide does not cover at all: Leaflet plugins and their replacements, the `@maplibre/maplibre-gl-leaflet` binding, clustering, drawing, non-Mercator sources, WMS, and any of the layer-per-feature consequences of Leaflet's DOM model. The three probes that survived all sit in that uncovered territory.

## What the rubrics guard against

Every tripwire below is a string the baseline actually produced, added after the run that produced it, and every one names something verified not to exist. Each is paired in its rubric with the real API beside it.

- **Test 1** — `not-icontains: .getMap()` and `not-icontains: maplibre-gl-leaflet@0.0`. The binding's accessor is `getMaplibreMap()` ([API.md](https://github.com/maplibre/maplibre-gl-leaflet/blob/main/API.md)) and its published versions are 0.1.x (latest 0.1.4); the baseline invented `.getMap()` in one run and pinned `maplibre-gl-leaflet@0.0.13` in another. The `icontains` on `@maplibre/maplibre-gl-leaflet` is the load-bearing assertion: the unscoped `maplibre-gl-leaflet` is a 404 on the npm registry, so an install line without the scope does not work.
- **Test 2** — `not-icontains: maplibre/maplibre-gl-draw`, one substring that catches both invented forms the baseline used, the `@maplibre/maplibre-gl-draw` package and the `github.com/maplibre/maplibre-gl-draw` repo. Both are 404 (npm registry; GitHub API). The rubric requires a library that does exist — Terra Draw, maplibre-geoman, or mapbox-gl-draw, all listed in [awesome-maplibre](https://github.com/maplibre/awesome-maplibre) — and names the eight controls GL JS actually exports (`src/index.ts`: Navigation, Geolocate, Attribution, Logo, Scale, Fullscreen, Terrain, Globe), none of which draws.
- **Test 3** — `not-icontains: maplibre-gl-projection`. Neither `maplibre-gl-projection` nor the `mapbox-gl-projection` "fork" the baseline cited beside it exists on npm. The rubric's positive claim is that `projection` (root-level, default `mercator`, with `globe` and `vertical-perspective` as the alternatives per `projection_factory.ts`) changes display only, and that the fix is reprojection at the source.
- **Test 4** — no tripwire. Its `icontains` is the bare `maplibre-gl-leaflet` substring and its rubric explicitly declines to grade the package scope, because the point of a negative is over-application, not recall. Test 1 carries the recall requirement.

## Probes cut for passing at baseline

Six probes were written, run, and cut. This is the [cutting content the model already gets right](../../CONTRIBUTING.md#cutting-content-the-model-already-gets-right) rule applied before any content existed, and the list is the more useful half of this PR for whoever writes the skill: none of these belongs in it.

- **`{s}` subdomain token in a migrated `L.tileLayer` URL** — the baseline stated outright that MapLibre GL JS does not expand `{s}`, and gave the right fix (one `tiles` array entry per subdomain host, which MapLibre round-robins). It also volunteered a broken `map.transformRequest = ...` assignment as an alternative, which is a constructor option, not a settable property — a defect, but not one a Leaflet-migration skill is the right home for.
- **`mouseenter` with no layer id never fires** — the baseline diagnosed it correctly, showed `map.on('mouseenter', 'my-fill', ...)`, read `e.features[0]`, and set the cursor through `map.getCanvas().style.cursor`.
- **Leaflet.markercluster with 9,000 markers** — the baseline said `maplibregl.Marker` is a DOM element that cannot be clustered, then produced the full source-level answer: `cluster: true`, `clusterRadius`, `clusterMaxZoom`, layers filtered on `['has', 'point_count']`, and `point_count_abbreviated` labels.
- **A source and layer per feature, ported from Leaflet's layer-per-feature model** — the baseline rejected the loop and gave one source, few layers, data-driven expressions, and `map.on('click', 'layer-id', ...)` with `e.features`. This was the direct probe for the raster-vs-vector mental model on #76; the model does not need it.
- **`L.circle`'s metre radius against pixel-valued `circle-radius`** — the baseline led with "`circle-radius` in MapLibre GL JS is always expressed in screen-pixels, not in metres" and built the Turf-polygon fill layer. Its reasoning trace wandered over `circle-pitch-scale` and misstated that property's default, but the delivered answer was right.
- **`L.tileLayer.wms` and the absent `wms` source type** — the baseline said there is no built-in `wms` source type and produced the documented pattern: a `raster` source whose `tiles` entry is a GetMap URL with `bbox={bbox-epsg-3857}`, `width`/`height` matching `tileSize: 256`, and `crs=` for WMS 1.3.0 against `srs=` for 1.1.1. In two runs the only fabrication was a `maplibre-gl-wms` plugin, and only inside the reasoning trace, never in the delivered answer — too thin to tripwire.

The pattern across all six matches the analysis in [#67](https://github.com/maplibre/maplibre-agent-skills/issues/67): the model answers questions of structure and judgment, and fails on names. Every surviving probe is a name question, and each failure is a fabricated package presented as the standard choice, with an install line and a version pin attached.
